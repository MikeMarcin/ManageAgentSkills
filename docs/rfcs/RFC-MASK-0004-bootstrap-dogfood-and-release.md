# RFC-MASK-0004: Bootstrap cutover, native dogfood and bounded v1 closeout


## Summary

Prove MASK can manage its own implementation workflow and canonical skill repository without maintaining per-project skill forks. Complete the bootstrap-to-managed cutover, exercise native launchers/links and agent JSON usage, and document a reversible v1 installation.

## Scope and prerequisites

Own ManageAgentSkills `.mask.json`, `.mask/skill-config/**`, agent-facing instructions, user documentation, release notes and focused end-to-end tests. The corresponding AgentSkills manifest edit is a named cross-repository handoff performed by that repository's integrator; reference its commit rather than letting a MASK lane mutate unrelated AgentSkills cards. Both canonical skills must be integrated before final cutover.

No blanket migration of SampleReview, SamplePlanner, all home-directory skills or every device. No daemon, auto-update schedule, auto-push, account linking, installation telemetry, marketplace publishing or public repository conversion.

## Bootstrap lifecycle

A new implementation session uses START-HERE.md and the original supplied workflow in a temporary **real-directory** local copy, customized only via its two supported project-specific files. This is a documented one-time bootstrap exception, not ongoing distribution.

Before migration, identify every bootstrap-generated path and whether Git tracks it. Do not replace a real `.agents/skills/implement-rfc` tree with a symlink merely because the desired skill name matches. Retain an independent known-good copy of all user-owned skill content outside agent-discovery roots. For packet-created, unchanged bootstrap directories, the integrator can move them to an explicit non-discovery bootstrap-retirement location after byte comparison. Modified or unrecognized content is a blocker requiring review, not automatic deletion.

The MASK runtime has **no** special command that recursively imports/removes a real skill tree. Migration is a bounded, explicit implementation step recorded on a card. Existing tracked copies require a deliberate reviewed Git change by the integrator; local MASK operations never rewrite the project's tracked history.

After destinations are clear:

```text
mask init --source /absolute/path/to/AgentSkills --json
mask project register /absolute/path/to/ManageAgentSkills --json
mask project require implement-rfc manage-agent-skills --project /absolute/path/to/ManageAgentSkills --apply --dry-run --json
mask project require implement-rfc manage-agent-skills --project /absolute/path/to/ManageAgentSkills --apply --json
mask project register /absolute/path/to/AgentSkills --json
mask project require implement-rfc manage-agent-skills --project /absolute/path/to/AgentSkills --apply --json
```

The AgentSkills project's declaration is edited by its authorized integrator. Examples use placeholders that the agent resolves; do not assume both machines have the same home or checkout path. Running MASK management against a dirty skills checkout is a supported local authoring case with a warning; remote update remains blocked until the normal Git workflow commits/pushes it.

## Ignore rules and inherited artifacts

Commit `.mask.json` and `.mask/skill-config/**`. Ignore machine-generated links and `.mask/generated/**`. Prefer per-managed-entry rules when a project also keeps unrelated real skills; never add a blanket ignore that hides existing tracked project-local workflows. `doctor` warns about tracked/unignored links but does not rewrite .gitignore. If all entries are generated, whole `.agents/skills/` and `.claude/skills/` rules are acceptable for these two newly scoped repositories after inventory.

Native role adapters generated by implement-rfc are a separate optional concern. Keep their ownership/ignore policy explicit. Delete or replace the original Claude shim only during the verified bootstrap cutover; the shared renderer must never write it again. The two consumer skill links resolve to the same canonical payload, while their project facts remain distinct.

## Direct acceptance scenario

Use a scratch project and local source remote to demonstrate the public sequence: init, inspect capabilities, initialize manifest, register, require/apply, inspect links, repeat no-op, modify declaration, plan/guard apply, fetch/update, simulate refusal, inspect recovery, unregister while preserving the manifest. Capture actual CLI commands/exit results in the card, not a large generated evidence bundle.

Then perform a named local dogfood registration of ManageAgentSkills and AgentSkills under explicit implementation authority. Verify both projects resolve the shared implement-rfc but load their own context. Read/invoke a bounded local no-op/preflight workflow rather than starting an unrelated RFC. A real agent's discovery check, if available, records the host/version and skill visibility; absence is a stated limitation, not a fabricated PASS.

## Native platform support

Advertise native Windows and macOS only after their focused symlink and launcher cards pass. Linux is best-effort at v1 unless separately exercised; a Linux development container does not establish Windows/macOS behavior. Use the configured native platform-ready lanes for remaining tests; continue independent work rather than blocking on a human demonstration. A partial closeout may summarize complete code while leaving the appropriate support/RFC status unverified.

## Recovery and uninstall contract

Explain how to inspect pending operations, complete/rollback only recorded safe link operations, and abandon a removed project using `unregister --keep-links`. Normal unregister unlinks owned unchanged entries and leaves the project manifest/context. It does not delete the skill source or program checkout.

Removing the program is an explicit ordinary filesystem/Git operation by the user/agent after unregistering selected projects, not a destructive `mask uninstall --purge`. Preserve source history and backups. A direct Python invocation remains an escape hatch when the PATH launcher is missing. Do not claim an internal-state file is a backup of skill content.

## Release and extensibility

Publish a local v0.1.0 readiness note containing supported Python/OS assumptions, invocation examples, actual native results, known limitations and excluded features. No mandatory public release or package registry upload. Repository licensing/visibility is an explicit owner decision.

Future winners can replace MASK because projects retain plain membership files, skills remain ordinary Agent Skills directories and no custom server exists. Per-project version pins, multiple sources, global skills, signed release distribution or remote fleet convergence require new RFCs rather than opportunistic additions to this one.


## Acceptance criteria

- **RFC-MASK-0004-AC01** — The two named repositories declare and resolve the same canonical implement-rfc and manage-agent-skills payloads, with distinct project context and no persistent project-specific skill forks.
- **RFC-MASK-0004-AC02** — Bootstrap retirement preserves user/modified/tracked content, clears only explicitly inventoried packet-created paths, and leaves shared SKILL.md unchanged through rendering and cutover.
- **RFC-MASK-0004-AC03** — A subprocess end-to-end scenario exercises noninteractive manifest/registry/link/update/refusal/recovery/no-op behavior with JSON/exit verification, not only unit tests.
- **RFC-MASK-0004-AC04** — Native Windows/macOS symlink and launcher evidence supports every advertised platform; unavailable lanes remain open and are named truthfully.
- **RFC-MASK-0004-AC05** — Agent instructions, install/update/recovery/unregister docs and ignore rules match the implemented CLI; no internal state editing or unsafe collision workaround is a normal management step.
- **RFC-MASK-0004-AC06** — Closeout records live baseline/integration/handoff commits and focused results, with no background service, sync engine, publication or unrelated project migration added.
